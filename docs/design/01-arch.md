# 群体智能演化系统 (SIES) 设计文档 V1.0

## 一、 系统愿景与核心理念

本系统旨在构建一个**去中心化、动态自适应的群体决策引擎**。通过引入链上不可篡改的历史数据，结合贝叶斯推断与群体智能（蚁群）算法，让参与者的“决策权重（信誉/话语权）”根据其历史表现进行客观、透明的演化。

**核心设计哲学：**

1. **不信任，只验证 (Trustless & Verifiable)**：所有决策输入、结果反馈和权重计算逻辑均在链上公开，任何人可验证其公平性。
2. **能力证明 (Proof of Competence)**：权重不依赖于初始财富或身份，而是基于历史决策质量的动态演化。
3. **抗女巫与反垄断 (Sybil & Oligopoly Resistance)**：通过时间衰减和边际收益递减机制，防止早期巨头永久垄断或恶意刷量。

## 二、 核心算法模型设计

权重的演化融合了**贝叶斯更新（微观概率修正）** 与**蚁群信息素机制（宏观时间衰减与正反馈）**。

### 核心抽象：信念-验证模型 (Belief-Verification Model)

在底层数学和博弈论模型中，投票和预测被统一抽象为同一种行为：**对不确定事件表达信念（Belief Expression），并接受事后验证（Outcome Verification）**。

- **Belief (输入)**：参与者对 $N$ 个互斥选项分配的权重向量。预测是连续概率分布（如 $[0.7, 0.3]$），投票是退化的离散分布（如 One-hot $[1.0, 0.0]$）或二次方投票的归一化权重。
- **Outcome (结果)**：事件结算时的真实状态（Ground Truth），同样表示为概率或确定性向量。
- **Scoring (评估)**：通过严格适当评分规则（Strictly Proper Scoring Rules）计算 Belief 与 Outcome 之间的散度/得分，作为贝叶斯更新的输入。
  这种抽象使得核心演化引擎无需感知具体业务场景，实现了极高的内聚和扩展性。

### 1. 基础演化公式

每个参与者 $i$ 在时间 $t$ 的权重 $W_{i,t}$ 由以下公式决定：
$$W_{i,t} = \underbrace{(1 - \rho) \cdot W_{i,t-1}}_{\text{蚁群挥发(时间衰减)}} + \underbrace{\Delta W_{bayes}}_{\text{贝叶斯更新(结果反馈)}} + \underbrace{\Delta W_{consensus}}_{\text{共识奖励(群体协同)}}$$

- **$\rho$ (挥发系数)**：蚁群算法中的信息素挥发率。防止“躺平”，要求参与者持续保持高质量的活跃度。
- **$\Delta W\_{bayes}$**：基于决策结果的后验概率修正。
- **$\Delta W\_{consensus}$**：基于群体智慧的协同奖励（如投票中促进共识达成）。

### 2. 贝叶斯更新机制 (Bayesian Updating)

将参与者的“决策能力”视为一个隐藏的概率分布。

- **先验分布**：假设参与者的准确率服从 Beta 分布 $Beta(\alpha, \beta)$。初始状态为 $Beta(1,1)$（均匀分布）。
- **似然函数**：当决策结果揭晓，若决策正确/盈利，$\alpha \leftarrow \alpha + 1$；若错误/亏损，$\beta \leftarrow \beta + 1$。
- **权重映射**：权重 $W$ 不仅看期望值 $\frac{\alpha}{\alpha+\beta}$，还要看**置信度（方差）**。对于高方差（参与次数少）的新手，系统会给予一个保守的基准权重（引入 Thompson Sampling 思想，平衡探索与利用）。

### 3. 场景化适配

#### 场景 A：投票 (Voting) - 聚焦“共识与质量”

在投票中，“正确”往往难以立即定义，因此引入**二次方投票 (Quadratic Voting)** 与**信念投票 (Conviction Voting)** 的变体：

- **事后验证奖励**：若提案执行后达到预期指标（通过链下预言机或DAO投票验证），支持该提案的权重获得贝叶斯正向更新。
- **少数派惩罚与保护**：若投票结果被证明是灾难性的（如黑客攻击提案），多数派权重挥发（$\rho$ 剧增），而提前预警的少数派获得极高的信息素奖励。

#### 场景 B：预测 (Prediction) - 聚焦“精度与校准”

预测市场有明确的“Ground Truth（真实结果）”，采用**严格适当评分规则 (Strictly Proper Scoring Rules)**：

- **Brier Score / Log Score**：根据预测概率与实际结果的偏差计算得分。预测概率越接近真实结果，$\Delta W_{bayes}$ 越大。
- **信息增益奖励**：如果参与者的预测在早期（市场不确定性高时）就指出了正确方向，其权重奖励高于在结果明朗后的“跟风”预测（引入时间加权因子）。

## 三、 区块链架构与数据层设计

为了实现“不可篡改、不信任只验证”，系统采用**状态通道 + 默克尔树 + 智能合约**的混合架构。

### 1. 链上数据模型 (On-Chain Data Schema)

所有核心状态均通过智能合约管理，保证确定性执行。

| 数据结构                     | 描述                                                                           | 存储位置                   |
| :--------------------------- | :----------------------------------------------------------------------------- | :------------------------- |
| **Identity (身份)**          | 用户的 DID、公钥、当前权重 $W$、Beta分布参数 $(\alpha, \beta)$、最后活跃时间。 | 链上 (State Trie)          |
| **Proposal (提案/事件)**     | 提案ID、描述哈希(IPFS)、截止时间、结果验证机制(Oracle/多签)。                  | 链上                       |
| **Ballot/Prediction (决策)** | 用户ID、提案ID、决策内容(选项或概率)、**决策时间戳**、质押金额(可选)。         | 链下签名 + 链上Merkle Root |
| **Resolution (结果)**        | 提案ID、真实结果(Ground Truth)、结算时间。                                     | 链上                       |

## 2.5 工程架构与模块划分 (Rust Workspace)

系统采用 Rust Workspace 组织，严格遵循依赖倒置和关注点分离原则：

- **`sies-core` (核心引擎)**：纯数学与逻辑层。包含 Belief/Outcome 抽象、评分规则、贝叶斯更新器、蚁群衰减算法。**零外部 I/O 依赖**，确保计算的绝对确定性。
- **`sies-storage` (存储抽象)**：定义 `StateStore` 和 `EventLog` 等 Trait，解耦核心算法与底层存储实现。
- **`sies-chain` (链上/验证层)**：负责状态树（Merkle Trie）、状态转换证明（State Transition）、ZK 电路接口或 Optimistic 欺诈证明逻辑。
- **`sies-api` (接口层)**：对外暴露 RPC、CLI 或 RESTful API，处理外部请求并调度核心引擎。

### 2. “只验证”架构设计 (Verifiable Computation)

由于每次投票/预测都进行复杂的贝叶斯和蚁群计算会消耗极高的 Gas，采用**乐观验证 (Optimistic Verification)** 或 **ZKP (零知识证明)** 架构：

- **方案 A：Optimistic Rollup 模式 (推荐用于高频场景)**
  - **链下计算**：链下节点（Sequencer/Aggregator）收集所有决策和结果，计算权重演化，生成新的状态树（State Root）。
  - **链上提交**：将 State Root 和状态转换证明提交到主链合约。
  - **欺诈证明 (Fraud Proof)**：挑战期内，任何人可验证计算过程。若发现计算错误，提交欺诈证明，作恶节点被 Slash（罚没质押），状态回滚。
- **方案 B：ZK-SNARKs 模式 (推荐用于高隐私/高安全场景)**
  - 链下生成权重更新的零知识证明（证明“我确实按照约定的贝叶斯和蚁群公式更新了权重，且没有篡改历史”），链上合约只验证 Proof，不暴露具体投票明细，实现**隐私保护与可验证性的统一**。

### 3. 防篡改与历史溯源

- 用户的每一次权重变更记录（Weight Delta Log）以 Append-only（仅追加）的方式写入链上或 Arweave/IPFS。
- 任何人可以通过回放历史事件（Replay），从创世区块重新推演出当前的权重分布，确保“代码即法律”。

### 4. 确定性与精度控制 (Determinism & Precision)

在分布式共识和区块链环境中，**严禁使用原生浮点数（如 f32/f64）**，因为不同 CPU 架构和编译器对浮点运算的舍入误差处理不同，会导致状态分叉（State Fork）。

- **定点数运算**：所有概率、权重、得分计算必须使用高精度定点数库（如 Rust 的 `rust_decimal`），或在链上映射为带有固定基数（如 $10^{18}$）的 `U256` 整数。
- **超越函数近似**：对于贝叶斯更新和 Log Score 中涉及的对数、指数运算，必须使用确定性的泰勒展开或帕德近似（Padé approximant），并固定迭代次数，确保所有节点计算出完全一致的比特级结果。

## 四、 业务流转机制 (Workflow)

### 1. 预测场景流转

1. **事件创建**：预言机或DAO创建预测事件（如“2026年11月美国大选结果”），设定结算时间。
2. **提交预测**：用户提交概率分布（如 A: 60%, B: 40%）。系统冻结用户部分基础权重或代币作为“皮肤在游戏里 (Skin in the game)”。
3. **结果结算**：事件到期，去中心化预言机（如 Chainlink/UMA）注入真实结果。
4. **权重演化**：
   - 合约/链下计算节点根据 Log Scoring Rule 计算每个用户的得分。
   - 执行贝叶斯 $\alpha, \beta$ 更新。
   - 执行蚁群挥发计算（距离上次活跃时间越长，挥发越多）。
5. **状态上链**：更新用户的链上权重状态。

### 2. 投票场景流转

1. **提案发起**：DAO发起资金分配提案。
2. **加权投票**：用户消耗“权重积分”进行投票。权重越高，选票影响力越大（可结合二次方函数 $\sqrt{W}$ 防止寡头）。
3. **结果追踪**：提案执行后，进入“回溯评估期”（如3个月后评估项目效果）。
4. ** retro-Weighting (回溯权重调整)**：根据项目实际产出，对当初投票支持/反对的人进行贝叶斯后验修正。

## 五、 系统安全与博弈论设计 (Game Theory)

为了防止系统被恶意攻击，必须在机制设计中纳入博弈论考量：

1. **抗共谋攻击 (Anti-Collusion / MACI)**
   - **问题**：大户在链下贿赂散户，让散户用低权重投票换取链下收益。
   - **对策**：引入**匿名投票与收据解绑**机制（如 Minimum Anti-Collusion Infrastructure, MACI）。用户可以随时在链上“覆盖”自己之前的投票，且只有最后一次投票有效，使得链下贿赂者无法验证散户是否真的履行了贿赂协议。
2. **搭便车问题 (Free-Rider Problem)**
   - **问题**：用户不主动研究，只复制高权重用户的决策。
   - **对策**：引入**信息熵惩罚**。如果某用户的投票向量与高权重用户的投票向量高度重合（余弦相似度极高），系统判定其为“跟风者”，降低其 $\Delta W_{consensus}$ 奖励，鼓励独立发现信息。
3. **质押与罚没 (Staking & Slashing)**
   - 参与权重演化计算的节点（如预言机、计算节点）必须质押代币。若提交虚假结果或错误计算，将被 Slashing。
